PROJECT CONTEXT 01 / VENA

Connected Healthcare Workflow

VENA는 관상동맥 협착 탐지 모델을 활용하는 의료 서비스와 의료진·환자 간 정보 전달을 모바일 환경에서 연결하기 위한 팀 프로젝트입니다.

의료진 앱에서는 환자 정보 조회, 검사 결과 접근, 의료진 간 채팅, 비동기 협진 및 업무 일정 관리를 지원하도록 구성했습니다.

환자 앱은 검사 이력, 의료진이 제공한 결과 정보, 예약 및 건강관리 기능을 중심으로 별도 개발되었습니다.

Room-based Sending Guard

ChatViewModel 
final sendingRoomIds = <String>{};

Future<void> sendMessage(
  String roomId,
  String content,
) async {
  final text = content.trim();

  if (text.isEmpty) return;

  if (sendingRoomIds.contains(roomId)) {
    return;
  }

  sendingRoomIds.add(roomId);
  notifyListeners();

  try {
    final message = await repository.send(
      roomId,
      text,
    );

    appendMessage(roomId, message);
  } finally {
    sendingRoomIds.remove(roomId);
    notifyListeners();
  }
}

채팅방별 전송 상태 관리 개념을 설명하기 위해 단순화한 예시입니다. 실제 소스의 전체 메서드가 아닙니다.

기능별 상태 독립성

Future<void> loadAllRequests() async {
  isLoading = true;
  notifyListeners();

  try {
    final results = await Future.wait([
      repository.getReceivedRequests(),
      repository.getSentRequests(),
    ]);

    receivedRequests = results[0];

bool includesDate(
  DateTime selected,
  DateTime start,
  DateTime end,
) {
  final day = DateTime(
    selected.year,
    selected.month,
    selected.day,
  );

  final first = DateTime(
    start.year, start.month, start.day,
  );

  final last = DateTime(
    end.year, end.month, end.day,
  );

  return !day.isBefore(first)
      && !day.isAfter(last);
}

List<dynamic> normalizeItems(dynamic body) {
  if (body is List) {
    return body;
  }

  if (body is Map) {

      'results',
      'patients',
      'data',

  );

Proposed Request Version Pattern
Proposed Dart Pattern 
int requestVersion = 0;

Future<void> loadItems() async {
  final version = ++requestVersion;

  isLoading = true;
  notifyListeners();

  try {
    final result = await repository.fetch();

    if (version != requestVersion) {
      return;
    }

    items = result;

  } catch (error) {
    if (version == requestVersion) {
      errorMessage = error.toString();
    }

  } finally {
    if (version == requestVersion) {
      isLoading = false;
      notifyListeners();
    }
  }
}

01 API CONTRACT

API는 화면과 서버의 계약이다.

환자, 채팅, 협진 및 메모 기능을 서버 API와 연결하면서 응답 구조와 상태 코드, 필수 입력값을 명확하게 정의하는 것이 중요하다는 점을 경험했습니다.

02 DATA CONSISTENCY

데이터는 저장 이후에도 관리된다.

일정과 To-do의 로컬 저장, 메모의 서버 저장, 협진 상태 변경을 구현하면서 데이터의 생성뿐 아니라 수정, 복원, 실패 및 동기화까지 고려해야 한다는 점을 확인했습니다.

03 ASYNCHRONOUS DESIGN

비동기 처리에는 상태가 필요하다.

API 요청과 파일 업로드는 즉시 완료되지 않으므로 진행 상태, 실패 처리, 중복 요청 및 결과 반영 시점을 함께 설계해야 한다는 점을 학습했습니다.

04 SECURITY BOUNDARY

화면 제어와 접근 권한은 다르다.

클라이언트에서 버튼을 제한하거나 인증 정보를 확인하는 것만으로는 서버 데이터의 접근 권한을 보장할 수 없습니다. 서버에서 검증해야 할 책임을 구분하는 관점을 얻었습니다.
